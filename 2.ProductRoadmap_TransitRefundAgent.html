Priya (Rider) Requirements — REQ-P
REQ-P01
Zero-Touch Proactive Refund
RIDER
As a daily commuter affected by a disruption, I want to automatically receive my refund without filing a claim, so that I don't have to spend time on administrative tasks after an already stressful journey.
AC: System identifies all eligible patrons within 5 minutes of disruption confirmation. Refund initiated without patron action. 100% of eligible patrons processed with no unclaimed refunds.
V1 MUSTCORE FLOWHIGH RICE: 648
REQ-P02
Real-Time Status Notification
RIDER
As a rider, I want to receive a push notification within 5 minutes of my refund being processed, so that I know it has been handled and don't need to follow up.
AC: Notification sent within 5 minutes of payment confirmation. Message includes: amount, method (card/credit), expected arrival time. Inquiry rate <1 per 100 patrons post-notification.
V1 MUSTNOTIFICATION
REQ-P03
Sub-90-Second Resolution Time
RIDER
As a rider, I want my standard refund to be processed within 90 seconds of a disruption being confirmed, so that I trust the system is fast and reliable.
AC: P50 <90s, P90 <5min, P99 <10min for all standard event types. SLA measured from disruption_confirmed timestamp to payment_gateway_confirmed.
V1 MUSTPERFORMANCE SLA
REQ-P04
Pass Holder Credit Notification (Personalised)
RIDER
As a monthly pass holder, I want to receive a notification explaining that my refund is applied as account credit (not a card refund), so that I'm not confused about where my money went.
AC: Notification copy differs based on payment_type. Pass holders see credit-specific message. Pass holder inquiry rate <0.5 per 100 patrons.
V1.x SHOULDPERSONALISATION
REQ-P05
Multi-Channel Notification (Push + SMS + Email)
RIDER
As a rider who doesn't use the mobile app, I want to receive my refund notification via SMS or email, so that I'm not excluded from proactive communication.
AC: System sends push notification (primary). Falls back to SMS if no app engagement in last 30 days. Email as tertiary. 99% patron reachability across all channels.
V1.x SHOULDCHANNELS
REQ-P06
Self-Service Dispute Portal
RIDER
As a rider who disagrees with a refund decision, I want to submit a dispute through the app that shows me exactly what the system decided and why, so that I can provide relevant information to have it reviewed.
AC: Patron sees decision summary in app. Dispute form pre-fills with case data. Dispute routes to HITL queue with full context. Patron receives status updates within 24hrs.

V1 SHOULDOBSERVABILITY

AC: Approved HITL decision (with justification) is indexed to RAG within 60 minutes. Future events of same type see confidence improvement ≥0.10. Supervisor is notified when a case they reviewed is now handled autonomously.

Anika (Finance) Requirements — REQ-F
REQ-F01
$500 Hard Cap at Payment API Layer
FINANCE
As the Finance Controller, I want a hard financial cap enforced at the payment API layer — not the prompt layer — so that no single autonomous refund can exceed $500 regardless of LLM output.
AC: Payment Gateway MCP Server rejects any refund request >$500 with AMOUNT_EXCEEDS_CAP. Rejection routes to HITL with financial alert. Cap is infrastructure-enforced — not bypassable by prompt content. 0 autonomous refunds >$500 in production.
V1 MUSTFINANCIAL SAFETY
REQ-F02
Immutable Audit Log — Every Decision Traceable
FINANCE
As the Finance Controller, I want an immutable audit log recording every refund decision — including the policy chunk used, confidence score, data inputs, and outcome — so that any payment can be reconstructed for audit within minutes.
AC: Audit log is append-only (no updates/deletes). Every entry includes: event_id, timestamp, agent_decisions[], policy_version, confidence_score, refund_amount, payment_status. Log queryable by event, patron, or date range. Retention: 7 years.
V1 MUSTCOMPLIANCE
REQ-F03
Idempotency — Zero Duplicate Payments
FINANCE
As the Finance Controller, I want the system to guarantee that each eligible patron receives exactly one refund payment, even in retry or crash-recovery scenarios, so that duplicate disbursements never occur.
AC: Idempotency key generated per patron per event. Payment Gateway MCP Server rejects duplicate key with 200 OK (not error). Zero duplicate refunds in 90-day shadow period and post-launch production.
V1 MUSTFINANCIAL INTEGRITY
REQ-F04
Financial Dashboard — Real-Time Disbursement Visibility
FINANCE
As the Finance Controller, I want a real-time dashboard showing total refunds disbursed (daily/monthly), error-correction costs saved, and any cap exceptions in HITL queue, so that I have full financial visibility without waiting for monthly reports.
AC: Dashboard shows daily and MTD disbursement totals. Cap exception count always visible. Error rate shown with 30-day trend. Data lag <5 minutes. Exportable to CSV for monthly CFO report.
V1 SHOULDFINANCIAL VISIBILITY
Rajan (Legal) Requirements — REQ-L & Sarah (VP) — REQ-VP
REQ-L01
PII Tokenization at MCP Server Boundary
LEGAL
As the Legal Officer, I want all patron PII (card numbers, travel history, contact details) to be tokenized before reaching any LLM, so that the AI system cannot leak personal data in its responses or logs.
AC: Passenger DB MCP Server tokenizes PII at query boundary. LLM receives token IDs, not raw data. Detokenization occurs only at notification delivery layer. PII never appears in LLM prompt or completion. Verified by security audit.
V1 MUSTDATA PRIVACY
REQ-L02
Prompt Injection Protection — Input + Output Rails
LEGAL
As the Legal Officer, I want the system to block adversarial inputs attempting to override AI instructions through patron-submitted data, so that no malicious input can cause the system to make unauthorised disbursements.
AC: NeMo input rails screen all patron-sourced data fields. Output rails validate response schema before any action is taken. Injection catch rate ≥94% (input rail) + 100% (output schema validation). Security test results documented.
V1 MUSTSECURITY
REQ-L03
Eligibility Bias Monitoring Report
LEGAL
As the Legal Officer, I want a monthly report showing eligibility approval rates segmented by route, time-of-day, and demographic proxy variables, so that I can detect any systematic bias in AI eligibility decisions.
AC: Monthly bias report auto-generated. Shows approval rates by: route, time_of_day, payment_type. Flags any segment with approval rate >2σ from mean. PM and Legal notified on flag. Bias remediation SLA: 5 business days.
V1 SHOULDRAI COMPLIANCE
REQ-VP01
Executive KPI Dashboard
VP OPS
As the VP of Operations, I want a single executive dashboard showing CSAT, straight-through rate, error rate, and cost savings in real time, so that I can report on ROI to the board without needing ops staff to compile data.
AC: Dashboard shows 5 board-level KPIs vs targets. Trend vs. pre-launch baseline always visible. Exportable to PDF for board deck. Accessible on mobile. Single source of truth for all ROI reporting.
V1 SHOULDEXECUTIVE REPORTING
REQ-VP02
Multi-Agency Architecture — V3 Platform Vision
VP OPS
As the VP of Operations, I want the refund agent architecture to be extensible to multiple transit agencies with isolated data and policy stores per agency, so that we can license the platform to generate new revenue streams.
AC: Architecture supports agency_id namespacing for all data stores. Policy MCP and Passenger DB MCP support multi-tenant configuration. First additional agency onboardable in <4 weeks. Isolation validated: agency A cannot access agency B data.

Quadrant Analysis
Strategic interpretation of positioning decisions
QUICK WINS → BUILD FIRST
Zero-touch refund, sub-90s SLA, push notification, HITL queue — all high value, moderate effort. These deliver the CSAT lift that justifies the entire investment. V1 core.
STRATEGIC BETS → INVEST CAREFULLY
Multi-agency platform, predictive pre-staging. High value but high effort. V3. Require separate ROI case before committing engineering resources.
FILL-INS → DO WHEN CAPACITY ALLOWS
Bias monitoring report, email notifications, pass holder personalisation — low effort, moderate value. Ship in V1.x patches or early V2 to add polish.
DEPRIORITISE → CHALLENGE ASSUMPTIONS
Self-service dispute portal, real-time disruption prediction — high effort, value uncertain. Require further discovery before committing. Not in current scope.

RICE Framework Calibration
How we defined each dimension for this product
REACH
# of patrons affected per disruption event. Scaled: 1=<100, 3=100–500, 5=500–2000, 8=2000–10K, 10=all 4.2M riders
IMPACT
Business value on 5-pt scale: 1=minimal, 2=low, 3=medium, 5=high, 10=massive. Composite of CSAT lift + cost saving + risk reduction.
CONFIDENCE
% certainty about Reach and Impact estimates. 100%=measured data. 80%=strong evidence. 60%=informed estimate. 40%=hypothesis.
EFFORT
Engineering-months (1 person for 1 month = 1). Estimated with tech lead. Includes: design, build, test, deploy. Not including PM time.

How to read this table as a PM

Release Themes
Each release has a clear PM narrative
V1.0 · JAN 2024 · "TRUST THE SYSTEM"
Prove that AI can handle the 62% of events (signal failures + power outages) with zero errors and 90s resolution. Build trust with ops team and Finance before expanding scope.
V1.x · APR 2024 · "POLISH & PERSONALIZE"
Add the quality-of-life features that take CSAT from 4.2 to 4.7. Hybrid RAG, per-type confidence thresholds, email channel, pass holder messaging. Experiment-driven.
V2.0 · JUL 2024 · "EXPAND THE SCOPE"
Add infrastructure faults and weather disruptions — bringing coverage to 14 event types. V1 reliability track record justifies expanding automated scope.
V3.0 · Q4 2024 · "PLATFORM PLAY"
Multi-agency architecture, cross-agency memory, self-service dispute portal. Conditional on V2 performance metrics being met. Separate business case required before commitment.
