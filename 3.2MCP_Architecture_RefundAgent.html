MCP — MODEL CONTEXT PROTOCOL · WHAT IT IS & WHY IT MATTERS
⬡ What is MCP?
MCP is an open standard protocol (by Anthropic, 2024) that defines how LLMs connect to external tools, data sources, and services. Think of it as USB-C for AI — a universal connector so any LLM can talk to any tool without custom integrations.

Before MCP, every LLM-tool integration was bespoke — different API shapes, auth patterns, error handling. MCP standardises the entire contract: how tools are discovered, how they're called, how results come back, how context is managed.
🔌 The Three Roles
MCP Host — the LLM application (our Orchestrator Agent). Decides which servers to connect to and manages the overall session.

MCP Client — lives inside the host. Maintains one-to-one connections with each server. Handles protocol-level communication.

MCP Server — exposes a specific capability (GTFS data, payment gateway, policy store). Lightweight, single-purpose, language-agnostic.
🛠 Three Primitives
Tools — functions the LLM can call. Defined with JSON Schema. Examples: get_gtfs_trips(), fire_refund().

Resources — data the LLM can read. Like a filesystem. Examples: policy documents, trip records, audit logs.

Prompts — reusable prompt templates. Examples: eligibility reasoning template, refund explanation template for patrons.
🚇 Why MCP in This Project?
Six agents, each needing different external capabilities. Without MCP: 6 × N custom integrations = unmaintainable spaghetti.

With MCP: each capability becomes one standardised server. The LLM discovers tools at runtime. Swapping from one payment gateway to another = swap one server, zero prompt changes.

Critical for auditability — every tool call is a structured, logged JSON-RPC message. Not a black-box LLM action.
MCP PROTOCOL ANATOMY
Every MCP interaction is a JSON-RPC 2.0 message over one of two transports: stdio (local process, low latency) or SSE (HTTP Server-Sent Events, remote server). Our project uses stdio for co-located agents and SSE for the payment gateway (remote, regulated).

Host → Server: initialize handshake
// Request (Host → GTFS MCP Server) { "jsonrpc": "2.0", "method": "initialize", "id": 1, "params": { "protocolVersion": "2024-11-05", "capabilities": { "tools": { "listChanged": true }, "sampling": {} }, "clientInfo": { "name": "transit-refund-orchestrator", "version": "2.1.0" } } } // Response (GTFS MCP Server → Host) { "jsonrpc": "2.0", "id": 1, "result": { "protocolVersion": "2024-11-05", "capabilities": { "tools": {}, "resources": { "subscribe": true } }, "serverInfo": { "name": "gtfs-mcp-server", "version": "1.4.2" } } }
② TOOL DISCOVERY — LLM lists available tools
Host → Server: tools/list to discover capabilities at runtime
// Request { "jsonrpc": "2.0", "method": "tools/list", "id": 2 } // Response — tools injected into LLM context { "result": { "tools": [ { "name": "get_gtfs_trips", "description": "Get all trips on a line within time window", "inputSchema": { "type": "object", "properties": { "line_id": { "type": "string" }, "start_time": { "type": "string", "format": "time" }, "end_time": { "type": "string", "format": "time" } }, "required": ["line_id", "start_time", "end_time"] } } // ... 3 more tools ] } }
③ TOOL CALL — Analysis Agent calls get_gtfs_trips()
LLM generates function call → MCP Client serialises → sent to GTFS Server
// Request (Analysis Agent → GTFS MCP Server) { "jsonrpc": "2.0", "method": "tools/call", "id": 7, "params": { "name": "get_gtfs_trips", "arguments": { "line_id": "BLUE", "start_time": "06:15:00", "end_time": "09:30:00" } } } // Response (GTFS Server → MCP Client → Agent context) { "jsonrpc": "2.0", "id": 7, "result": { "content": [ { "type": "text", "text": "{\\"trips\\":[\\"TRP-0001\\",...\\"TRP-1247\\"],\\"count\\":1247,\\"line\\":\\"BLUE\\"}" } ], "isError": false } }
④ TOOL CALL — Payment Agent fires initiate_refund() via SSE
SSE transport (HTTP) — payment gateway is remote. mTLS auth required. $500 cap enforced here.
// POST https://payment-gateway/mcp/sse // mTLS + Bearer token required { "jsonrpc": "2.0", "method": "tools/call", "id": 142, "params": { "name": "initiate_refund", "arguments": { "patron_token": "TKN-982-B4F2", "amount": 27.90, "currency": "USD", "payment_method": "CREDIT_CARD", "idempotency_key": "DIS-2024-0847-TKN-982-B4F2", "disruption_ref": "DIS-2024-0847" } } } // Response — payment confirmed { "id": 142, "result": { "content": [{ "type": "text", "text": "{\\"status\\":\\"SUCCESS\\",\\"txn_id\\":\\"TXN-4F2C-8841\\",\\"amount\\":27.90}" }], "isError": false } } // ⚠ If amount > 500 — server returns error: // "isError": true, "code": "AMOUNT_EXCEEDS_CAP"
⑤ RESOURCE READ — Eligibility Agent reads policy document
Resources = data the LLM reads directly (not tool calls). Policy PDFs exposed as MCP resources.
// List available resources { "method": "resources/list", "id": 12 } // Response: [{uri:"policy://signal-failure-v2022", // name:"Signal Failure Refund Policy 2022", // mimeType:"application/json"}] // Read specific resource { "method": "resources/read", "id": 13, "params": { "uri": "policy://signal-failure-v2022" } } // Response: policy document injected into LLM context { "result": { "contents": [{ "uri": "policy://signal-failure-v2022", "mimeType": "text/plain", "text": "Section 4.2 Signal Failure Policy..." }] } }
⑥ AUDIT WRITE — Guardrail Agent logs compliance record
Every agent writes to Audit Log MCP Server after each action. Immutable. Cannot be deleted.

MCP END-TO-END WORKING — STEP BY STEP
PHASE 01 · STARTUP · T-before-event
Host Initialises 6 MCP Client Sessions
Before any disruption event arrives, the LangGraph Orchestrator (MCP Host) boots up and creates one MCP Client session per server. Five sessions use stdio transport — the MCP server runs as a child process, communicating over stdin/stdout. The Payment Gateway session uses SSE transport — an HTTP connection to the remote gateway endpoint. Each client performs the initialize handshake and then calls tools/list to discover available tools. All 24 tools across 6 servers are loaded into the host's tool registry.
// 5 stdio sessions (co-located): gtfs_client = MCPClient(StdioTransport("./gtfs-server")) passenger_client = MCPClient(StdioTransport("./passenger-server")) policy_client = MCPClient(StdioTransport("./policy-rag-server")) notify_client = MCPClient(StdioTransport("./notify-server")) audit_client = MCPClient(StdioTransport("./audit-server")) // 1 SSE session (remote payment gateway): payment_client = MCPClient(SSETransport("https://gateway.api/mcp"))
stdio × 5 SSE × 1 tools/list
PHASE 02 · T+0s · ANALYSIS AGENT
LLM Decides to Call a Tool — MCP Serialises
The Analysis Agent receives the disruption state. The LLM generates a function call in its output: get_gtfs_trips(line_id="BLUE", start_time="06:15:00", end_time="09:30:00"). The MCP Client intercepts this, serialises it to a JSON-RPC 2.0 tools/call message, and sends it over the stdio pipe to the GTFS MCP Server process. The LLM never directly calls any API — MCP is the only bridge.
// LLM output → MCP Client serialises: {"jsonrpc":"2.0","method":"tools/call","id":7, "params":{"name":"get_gtfs_trips", "arguments":{"line_id":"BLUE", "start_time":"06:15:00", "end_time":"09:30:00"}}} → sent via stdio pipe → GTFS MCP Server process
JSON-RPC 2.0 tools/call stdio transport
PHASE 03 · T+2s · CRITICAL SECURITY BOUNDARY
PII Tokenization Happens at MCP Server — Never Reaches LLM Raw
The Passenger DB MCP Server is where PII tokenization is enforced. The Analysis Agent calls query_passengers(trip_ids=[...]) and tokenize_pii(records). The MCP server executes tokenization before returning results. The tool result that comes back to the LLM context contains only TKN-982-B4F2 — never the raw card number or patron name. MCP server = PII boundary. Even if the LLM was compromised and tried to exfiltrate PII, it never had it.
// Tool result returned to LLM context: {"patron_token": "TKN-982-B4F2", // ← never raw PII "fare_amount": 12.40, "payment_method": "CREDIT_CARD", // ← type only, not card# "trip_id": "TRP-0001"} // Raw card_number: 4532-xxxx-1234 stays in MCP server only
PII Boundary Security Critical Data Minimisation
PHASE 04 · T+4s · ELIGIBILITY AGENT
RAG via MCP — Hybrid Retrieval as Tool Calls
The Eligibility Agent calls two MCP tools on the Policy RAG Server: semantic_search(query="signal failure refund eligibility", threshold=0.7) and bm25_search(query="SIGNAL_FAILURE Section 4.2"). The Policy RAG MCP Server executes both searches, merges results, and returns structured chunks including metadata (source document, version, section number). The LLM receives the chunks as a tool result — not as raw text injected into the system prompt. This means retrieval quality can be monitored independently of the LLM.
// Policy RAG MCP Server returns structured result: {"chunks": [ {"text": "Section 4.2: All fare-paying passengers...", "source": "Signal_Failure_Policy_v2022.pdf", "section": "4.2", "relevance": 0.94, "effective_date": "2022-03-01"}, ... ], "retrieval_latency_ms": 161}
semantic_search bm25_search Structured chunks
PHASE 05 · T+14s · GUARDRAIL AGENT
NeMo Rails Wrap Every MCP Tool Call and Result
NeMo Guardrails operate as a middleware layer around the MCP client. Before any tools/call request leaves the agent, the NeMo input rail scans for adversarial patterns. After any tool result arrives, the NeMo output rail validates the content. This means guardrails are applied at the protocol layer — not inside the LLM prompt. A compromised or drifted LLM cannot bypass guardrails by generating a malformed tool call — the MCP client rejects it before it even reaches the server.
// NeMo wraps MCP client: class GuardedMCPClient(MCPClient): async def call_tool(self, name, args): await nemo.input_rail(name, args) # BEFORE result = await super().call_tool(name, args) await nemo.output_rail(name, result) # AFTER return result
NeMo Middleware Protocol-level Pre + Post validation
PHASE 06 · T+22s · PAYMENT AGENT
$500 Cap Enforced at Payment MCP Server — Not the Prompt
The Payment Agent calls initiate_refund(amount=27.90, patron_token="TKN-982") on the Payment Gateway MCP Server via SSE. The SSE server is deployed at the payment gateway's API boundary — it is effectively the gateway's MCP adapter. The $500 cap is enforced here: if the LLM generates a tool call with amount=550, the MCP server returns isError:true, code:"AMOUNT_EXCEEDS_CAP". No prompt engineering change can override this — it is infrastructure enforcement.
// SSE transport (HTTP POST to remote gateway): // mTLS + Bearer JWT required // idempotency_key prevents double-refund on retry {"name":"initiate_refund", "arguments":{"patron_token":"TKN-982-B4F2", "amount":27.90, "idempotency_key":"DIS-2024-0847-TKN-982"}} // Server enforces: if amount > 500 → AMOUNT_EXCEEDS_CAP error
SSE transport $500 Cap at API Idempotency Key
PHASE 07 · T+25s · ALL AGENTS
Every Action Written to Audit Log via MCP
Every agent writes to the Audit Log MCP Server after each significant action. The write_audit_entry() tool is append-only — the server exposes no delete or update tool. This is by design: the immutability is enforced at the MCP server layer, not by policy. A compromised agent cannot rewrite history because the tool simply doesn't exist on the server. Each audit entry includes the agent name, timestamp, action, result, and a SHA-256 hash of the entry — enabling tamper detection.
// Called by every agent — cross-cutting concern: write_audit_entry({ event_id: "DIS-2024-0847", agent: "payment_agent_v2.1", action: "REFUND_INITIATED", result: {txn_id:"TXN-4F2C",status:"SUCCESS",amount:27.90}, hash: sha256(entry) }) // Server: append-only write. No delete/update tool exists.
Append-only SHA-256 hashed Cross-cutting
⬡ MCP vs Direct API Calls
Without MCP: each agent has custom code to call GTFS API, handle auth, parse response, manage errors. 6 agents × 6 systems = 36 bespoke integrations.

With MCP: each agent calls mcp_client.call_tool("get_gtfs_trips", args). Same interface for all tools. Swap the GTFS provider → replace one MCP server. Zero agent code changes.

Interview punchline: MCP is what makes this architecture maintainable at scale.
🔌 stdio vs SSE — When to Use Which
stdio — local process, sub-millisecond latency, no network overhead. Used for co-located servers (GTFS, Passenger DB, Policy RAG, Notification, Audit).

SSE — HTTP transport, works across network boundaries. Used for Payment Gateway because: (1) it's a remote regulated service, (2) mTLS auth required at HTTP layer, (3) $500 cap enforced at the HTTP API endpoint itself.
🛡 MCP as a Security Boundary
Three security properties enforced at MCP layer, not prompt level:

1. PII never reaches LLM — tokenization in Passenger DB MCP Server.
2. $500 cap unbreakable — enforced in Payment MCP Server API.
3. Audit log immutable — no delete tool on Audit MCP Server.

Why this matters: prompt engineering can be jailbroken. MCP server APIs cannot.
📐 MCP Tool Schema = PM Spec
Each tool's inputSchema (JSON Schema) is effectively a PM-authored contract. Writing the schema for initiate_refund() — what fields are required, what types, what constraints — is a product decision, not an engineering one.

The schema is what the LLM sees when it decides whether and how to call a tool. Schema quality = tool call quality.
